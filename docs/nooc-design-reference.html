How it is built

One token layer, two consumers that ignore it

Nooc is a Next.js 14 app styled with Tailwind and shadcn/ui components. The design tokens live in one file — app/globals.css — as HSL triplets on :root, which tailwind.config.ts maps onto Tailwind color names.

Token flow

app/globals.css defines --primary: 151.8 68.8% 18.8% → tailwind.config.ts maps it as primary: "hsl(var(--primary))" → components use bg-primary, text-primary.

Because tokens are stored as bare HSL channel values (not full colors), they only work through the hsl(var(--x)) wrapper. Any surface that can't read CSS variables — transactional email, the Mapbox canvas, generated PDFs — hard-codes its own hex values instead. The token is now chosen so it resolves to exactly the hex those surfaces already use; see Brand green.

Inconsistency — worth a decision

Two neutrals are cool, not warm. --foreground (222 47% 11%) and --muted-foreground (215.4 16.3% 46.9%) are shadcn's stock slate values and were never re-tuned to the warm 30° family used by every background, border and surface token. In practice this puts blue-grey text on sand-tinted paper throughout the app.

Verified — dark mode never activates

Tailwind is set to darkMode: ["class"], but nothing in the codebase ever applies the dark class. There is no theme provider, no toggle, no prefers-color-scheme listener, and no next-themes dependency. Only 7 dark: utilities exist across the whole app, all on red/green status text.

Treat the dark palette as an untested draft, not a shipped theme. Its greens were moved into the new brand hue for consistency, but nothing beyond that was designed or tested — if dark mode is picked up later it needs a proper contrast pass.

Inconsistency

Green and emerald are used interchangeably for the same "success" meaning, and amber and yellow both stand for "warning." Neither pair is tokenized, so there is no single place to change them. A designer should collapse each pair to one ramp and promote it into globals.css.

Brand color

One brand green: #0F5132

Four different greens used to ship as “the brand green.” The three that live in code are now unified on #0F5132 — the value that was already labelled brandGreen in the source and already used by email, maps and printed stickers.

Why this exact HSL

The token is written as 151.8 68.8% 18.8% rather than a rounded 152 69% 19% because only those decimals round-trip to exactly #0F5132. That matters: email, map pins and print hard-code the literal hex, so an approximate token would leave a visible mismatch between a button and the confirmation email for the same booking. Verified in the browser — hsl(var(--primary)) computes to rgb(15, 81, 50).

Still divergent — deliberately left alone

The logo artwork is a different green. The mark is #274229 — noticeably more olive (hue 126° against the brand's 152°) — and the splash screen is #052A10. Both live inside raster PNGs, not code.

These were not touched, because recoloring them means algorithmically remapping anti-aliased pixels in artwork that has no vector master. That would degrade the mark rather than fix it. Correcting these is a design task: redraw the mark as vector at #0F5132, then re-export the icon, splash and email assets. The splash's config color (#052A10 in capacitor.config.ts) must change in lockstep with its artwork or a seam appears.

Typography

The product is set in Inter — as of now, actually

Fixed — Inter had been configured but never applied

app/layout.tsx had always loaded Inter via next/font/google and exposed it as --font-inter on <body>. But tailwind.config.ts never extended fontFamily.sans to point at that variable, so font-sans fell through to Tailwind's stock stack. The product rendered in the OS UI font — SF Pro, Roboto or Segoe UI depending on platform — while still downloading the Inter woff2 on every page load.

The theme now maps sans to ["var(--font-inter)", ...defaultTheme.fontFamily.sans]. Confirmed in a running build: <h1> computes to the Inter face, document.fonts.check() returns true, and the face reports loaded rather than unloaded.

What the switch did to layouts

Inter is marginally wider than SF Pro, so this was tested rather than assumed. Every text-bearing element on each page was measured twice — once in Inter, once with the old system stack forced back on — and compared for new clipping or added height.

Pre-existing layout issue — not caused by the font, not fixed here

On the venue detail page at 375px, a long venue name wraps to five lines (“Black Milk Coffee and Crepe”). This is not a font regression — measured with Inter and with the old system font, it wraps to five lines either way. The cause is that the title's container is only 135px wide on a 375px viewport, because the header row lets four circular icon buttons take the rest. Worth a designer's attention as a layout fix.

Shape & elevation

A 16px corner radius, on a scale that finally runs in order

Fixed — the scale used to run backwards

Previously only sm, md and lg were derived from --radius while xl, 2xl and 3xl kept Tailwind's defaults. Because --radius had been raised to 1rem, the ranges overlapped: rounded-xl (12px) came out smaller than rounded-md (14px) and equal to rounded-sm, and rounded-2xl (16px) was identical to rounded-lg. Picking a corner by name gave you something other than what you meant.

All seven steps now derive from --radius, and a 4xl step was added so the large panel corners already in use have a name. Verified in the browser: 12 · 14 · 16 · 20 · 24 · 32 · 40.

The migration was pixel-preserving

Because the numbers behind several names moved, 99 class usages across 26 files were remapped so every corner in the product still renders at exactly the radius it did before. Nothing about the product's shape changed — only the vocabulary describing it. This also retired every hand-written arbitrary radius.

Card

The primitive is plain shadcn: rounded-lg (16px) · border · bg-card (#FFFFFF) · shadow-sm. Sub-parts use 24px padding (p-6), and CardTitle is text-2xl / 600 / tracking-tight.

Drift — the primitive is usually overridden

Product surfaces rarely use the card as shipped. The venue booking panel, for example, renders as border-none bg-white shadow-lg rounded-2xl — 24px corners, no border, heavier shadow — and venue cards override padding to p-4 and titles to text-lg. The real card style is the override, not the primitive. Worth reconciling.

Input

Primitive: h-10 (40px) · rounded-md (14px) · 1px --input border · bg-background · text-sm · px-3 py-2 · focus ring 2px + 2px offset.

Note the height mismatch with buttons: inputs are 40px, the default button is 48px, so a field and its adjacent button don't align without intervention. In the live search form, inputs are further overridden to bg-white, border-muted/60, shadow-sm, and a 1px focus ring in --primary instead of the standard 2px offset ring.

Bottom navigation

The primary chrome on mobile and the app. components/layout/BottomNav.tsx.

  • Fixed, full width, z-50, .glass with a border-white/20 top edge.
  • Measured height 87px on web; the component publishes its own real height to --bottom-nav-height via ResizeObserver so sticky bars above it can reserve exact space.
  • Items: Explore (Home icon), Reservations (Calendar), Profile/Login (User), plus Manage (Laptop) only for venue owners — so the nav is 3 or 4 items depending on the account.
  • Icons are Lucide at 22px; stroke width shifts 2 → 2.5 when active.

Dialog & sheets

Radix-backed. Overlay is bg-black/80 with fade. Content: centered, max-w-lg, p-4 rising to p-6 at sm, shadow-lg, max-h-[90vh] scrolling, corners only rounded at sm and up (full-bleed on mobile). Toast

Fixed top-center, z-50, rounded-lg, px-4 py-3, shadow-lg, 4s auto-dismiss, 14px medium text with a manual close button.

  • Success — bg-green-50, border-green-200, text-green-900, with a CheckCircle2 icon in green-600.
  • Error — bg-red-50, border-red-200, text-red-900, no icon.

Only these two states exist — there is no info or warning toast.

Loading spinner

An inline SVG circle, r=10, stroke-width 3, round caps, stroke-dasharray "32 100" (an arc of roughly 51% of the circumference), animate-spin, colored text-primary. Two sizes only: sm 16px, md 20px.

Iconography

Lucide React throughout (lucide-react 0.424). Default 2px stroke, raised to 2.5 for active nav. Common sizes: 14px (h-3.5) for inline meta, 16px (h-4) for buttons and close, 20–22px for nav, 40px (h-10) for empty states. No custom icon set.

Press feedback — the most consistent interaction signature

active:scale-[0.98] · 8 active:scale-95 · 7 active:scale-90 · 5 active:scale-[0.99] · 3 active:scale-[0.97] · 1

Almost every tappable element shrinks on press, scaled inversely to its size — large surfaces barely move (0.99), small circular icon buttons compress hard (0.90). Entrance animations come from tailwindcss-animate: animate-in, fade-in, zoom-in, slide-in-from-*.

Accessibility gap

There is no prefers-reduced-motion handling anywhere in the codebase. Every transform, scale and entrance animation plays regardless of the user's system setting.

Safe areas — a real design constraint

The iOS WebView runs with contentInset: "never" (required to stop position: fixed elements drifting during scroll), so the WebView spans the entire screen and all safe-area spacing is handled in CSS, not by the OS. Anything you design that anchors to a screen edge must account for this:

Token / classWebNative app
--safe-area-top0pxenv(safe-area-inset-top) + 10px
--bottom-nav-height4.25rem (68px)4.25rem + env(safe-area-inset-bottom)
.safe-area-topApplies top: var(--safe-area-top) — for fixed, full-bleed elements that must start below the status bar
.status-bar-scrimNative-only opaque strip in --background at z-60, so scrolled content doesn't slide under the clock and Dynamic Island

The extra +10px on the top inset is a deliberate buffer: iOS reports the Dynamic Island's resting height, but the cluster grows taller while showing a transient indicator (such as the location-in-use arrow that Nooc's own “Use my location” triggers), and CSS can't detect that state.

The offline fallback page (mobile/www/index.html) is styled independently in plain CSS, and now uses the same values as the app: #fbfaf9 ground, #0f172a text, #64748b secondary, #0f5132 accent, 1rem and 1.25rem radii, system font stack. It deliberately stays on the system stack — it is the page shown when the network is unavailable, so it cannot depend on a web font loading.

Capacitor copies mobile/www/ into ios/App/App/public/ and android/…/assets/public/ on cap sync. Those copies are gitignored build artifacts — mobile/www/ is the source of truth; run a sync after changing it.

Asset gaps

There is no vector master. Every logo asset in the repository is a raster PNG at a non-square 798×862, including the favicon and touch icon — so the mark cannot be rendered cleanly at arbitrary sizes, recolored, or used in print without redrawing. There is also no wordmark asset: the Nooc wordmark in email is set in live text, not artwork.

Two untracked logo files sit loose in the repository root rather than in public/, and four separate copies of the same 343KB artwork are committed under different names.

Open decisions

What's settled, and what a designer should take next

Three of the eight items in the first edition of this reference have been resolved in code. The rest need a designer, not an engineer — they are judgement calls about how the product should look, not defects with an obvious correct answer.

Still open

1 · Redraw the logo as vector, in the brand green

The mark is #274229 and the splash is #052A10, both raster-only. This is now the single remaining source of brand-color inconsistency, and it can't be fixed in code — it needs the mark redrawn as vector at #0F5132 and re-exported to favicon, touch icon, iOS app icon, email logo and splash. The splash's capacitor.config.ts color must move with its artwork or a seam appears at launch.

2 · Fix the venue-title header on mobile

At 375px the venue name gets a 135px-wide container because four circular icon buttons take the rest of the header row, so a normal café name wraps to five lines. Independent of the font — it wraps identically either way. Needs a layout decision: wrap the actions, shrink them, or move them.

3 · Tokenize status color

Green and emerald both mean success; amber and yellow both mean warning. None are tokenized, so there's no single place to change them. Collapse each pair to one ramp and lift them into globals.css alongside the other tokens.

4 · Reconcile the card primitive with reality

The shipped Card (16px radius, bordered, shadow-sm, 24px padding) is overridden nearly everywhere it's used — most real cards are borderless, 24px-cornered and shadow-lg. Redefine the primitive to match the real pattern, or define named variants.

5 · Warm the two cool neutrals

--foreground and --muted-foreground are still shadcn's stock slate while every other neutral was tuned to a warm 30° hue, so text reads slightly blue against warm paper. Left alone deliberately — retuning body text color across the whole product is a design call.

6 · Decide whether dark mode is real

A full dark palette exists and is unreachable — no toggle, no provider, no media query. Its greens were kept in the brand hue during this pass, but nothing was designed or contrast-tested. Either design and ship it, or delete it so it stops implying support.

7 · Fill the primitive and accessibility gaps

There's no badge primitive despite badges appearing throughout; inputs (40px) and buttons (48px) don't align when placed side by side; and there is no prefers-reduced-motion handling anywhere, so every scale and entrance animation plays regardless of the user's system setting.
